# Бюджет размера

Размер — требование, а не пожелание (ADR-11). Он держится тремя механизмами: правилами кода, флагами сборки и проверкой в CI.

## 1. Бюджеты

| Бинарник | TinyGo (релиз) | gc |
|---|---|---|
| `examples/hello` | ≤ 64 КБ (спайк S3 — 35 952 байта) | замер S1 + 10 % ≈ 1 625 000 байт (S1 — 1 477 448) |
| `examples/form` (все виджеты MVP) | ≤ 160 КБ (оценка) | hello (gc) + 200 КБ |
| `examples/logger` | **≤ 250 КБ** | hello (gc) + 300 КБ |

Цифры с пометкой «оценка» уточняются по итогам S1/S2 и фазы 2, после чего фиксируются в `size-budget.txt`. Дальше они меняются только отдельным коммитом с объяснением, на что ушли байты.

## 2. Откуда берётся размер

**gc.**
- Около 1 МБ — неустранимый «пол»: рантайм (планировщик, сборщик мусора, стеки горутин), таблица `pclntab` (имена функций и номера строк для паник и трассировок) и метаданные типов.
- Сверху добавляется всё, что затянули импорты. `fmt` тянет `reflect`, `strconv`, `unicode` и `sync` — это сотни КБ.
- Компоновщик gc выбрасывает недостижимые функции, но метаданные типов и инициализация пакетов остаются.

**TinyGo.**
- Рантайм занимает единицы и десятки КБ.
- LLVM удаляет всё недостижимое вплоть до отдельных функций и глобальных переменных, а `-opt=z` оптимизирует по размеру.
- Главные «пожиратели» — `fmt`, `reflect`, `time` с форматированием, `encoding/*`, `math/big`, `crypto/*`, большие таблицы `unicode`.

**C-часть** (обёртки) весит единицы КБ. Плюс таблица динамического импорта (около 100 символов GTK) — ещё несколько КБ.

Ожидаемая структура `examples/logger` в TinyGo (оценка, сверить в фазе 4):

| Часть | КБ |
|---|---|
| рантайм TinyGo + GC | 10–20 |
| nui (используемые виджеты, ядро) | 30–50 |
| C-обёртки, PLT/GOT, динамические секции ELF | 10–15 |
| логика приложения (файлы, порт, строки) | 50–100 |
| строковые константы, данные | 10–20 |
| **итого** | **≈ 110–205** |

## 3. Правила кода (`nui` и `internal/*`)

1. **Белый список прямых импортов:** `unsafe`, `sync`, `sync/atomic`, `errors`, `runtime`, `unicode/utf8`, `unicode/utf16` (только `*_windows.go`), `C` и собственные `nui/internal/*`. Больше ничего. Проверяется `make deps`.
2. **Без `fmt`, `strconv`, `strings`, `time`, `os`, `path`, `sort`, `reflect`, `encoding/*`, `log`.** Немногие нужные вещи пишутся руками в `internal/core/text.go`, по несколько строк каждая:
   - `itoa` для отладочных сообщений;
   - `FixUTF8` — замена битых последовательностей UTF-8 на U+FFFD (для `cstr`, [runtime.md](runtime.md), §12);
   - `dir(path)`.
3. **Без горутин, каналов, `select`** в ядре (ADR-7).
4. **Реестры — срезы, а не `map`.** Карты в TinyGo тянут хеширование и сами по себе больше.
5. **Без `any`/`interface{}` в API.** Интерфейсов всего два: запечатанный `Widget` и `core.Receiver`.
6. **Без обобщённых (generic) функций в ядре.** В TinyGo каждая инстанциация — отдельная копия кода.
7. **Сообщения паник и ошибок — строковые константы** без форматирования: `"nui: виджет уже вставлен в контейнер"`.
8. **Никаких таблиц, которые «держат всё».** Например, `map[Kind]func()` со ссылками на все конструкторы сделает их все достижимыми, и DCE перестанет работать. Каждая функция `drv` вызывается только из «своего» метода nui. Тогда цепочка «метод не вызывается → функция drv не нужна → C-символ выброшен `--gc-sections`» работает до конца.
9. **В `init()` — только `runtime.LockOSThread()`.** Глобальные переменные нулевые или маленькие.
10. **Проверка DCE при добавлении виджета:** размер `examples/hello` в TinyGo не должен вырасти ни на байт, в gc — не больше чем на 1 КБ: у gc выравнивание секций и порядок символов сдвигают размер на сотни байт даже без нового кода ([architecture.md](architecture.md), чек-лист).

В тестах (`*_test.go`) и `tools/` можно импортировать что угодно: в бинарник приложения они не попадают.

**Приложения** (`examples/*`) могут использовать любые пакеты, но бюджет общий. В [acceptance.md](acceptance.md) описано, как логгер укладывается в 250 КБ без `fmt` и `time`.

## 4. Флаги сборки

**TinyGo, релиз:**

```sh
tinygo build -target=targets/linux-glibc-amd64.json -opt=z -no-debug -panic=trap -gc=conservative \
             -scheduler=none -o bin/small/hello ./examples/hello
strip --strip-all bin/small/hello
```

| Флаг | Зачем |
|---|---|
| `-target=targets/linux-glibc-amd64.json` | цель nui: системная glibc вместо musl из TinyGo — без этого GTK не загрузить (ADR-4, ADR-17) |
| `-opt=z` | оптимизация по размеру (по умолчанию тоже `z`; пишем явно) |
| `-no-debug` | без DWARF |
| `-panic=trap` | паника = инструкция-ловушка, без строк сообщений и кода печати. Для отладки — `-panic=print` |
| `-gc=conservative` | консервативный сборщик мусора; маленький и совместим с обёртками |
| `-scheduler=none` | без планировщика горутин. Приложению с горутинами — `-scheduler=threads` ([runtime.md](runtime.md), §15) |

**gc:**

```sh
go build -trimpath -ldflags="-s -w -buildid=" -o bin/hello ./examples/hello
```

**C-часть:** `-Os -ffunction-sections -fdata-sections` и `-Wl,--gc-sections -Wl,--as-needed`. Они передаются через переменные `CGO_CFLAGS` и `CGO_LDFLAGS` в Makefile, а не через `#cgo`: там gc их не пропускает ([driver-gtk3.md](driver-gtk3.md), §9). На mingw без `-fdata-sections` ([driver-win32.md](driver-win32.md), §1).

**Обязательно:** `strip --strip-all` после TinyGo: `-no-debug` убирает DWARF, но оставляет таблицу символов (спайк S3: 56 640 → 35 952 байт). Проверка: `file bin/small/hello` не должен показывать `not stripped`.

## 5. UPX

| За | Против |
|---|---|
| gc-бинарник сжимается примерно до 35–40 % | при каждом запуске распаковывается в память: +10–30 мс к старту, страницы не разделяются между процессами |
| | антивирусы (особенно на Windows) чаще считают упакованный файл подозрительным |
| | затрудняет отладку и анализ (`perf`, `gdb`, `ldd` видят упаковщик) |

Решение: UPX **не используется по умолчанию**. Для запасного варианта на gc есть отдельная цель `make small-upx`. Её результат в бюджет не входит и в CI не проверяется.

## 6. Как измерять

```sh
stat -c %s bin/small/logger                          # главное число

tinygo build -size full -target=targets/linux-glibc-amd64.json -opt=z … ./examples/logger
                                                     # размер по пакетам: code / rodata / data / bss

go build -trimpath -o /tmp/hello-dbg ./examples/hello  # gc: без -s -w, чтобы были символы
go tool nm -size -sort size /tmp/hello-dbg | head -40  # самые большие символы

size -A bin/small/logger                             # размеры секций ELF
readelf -d bin/small/logger | grep NEEDED            # какие .so реально подключены
nm -D --undefined-only bin/small/logger | wc -l      # сколько символов импортировано
```

Для разбора gc-бинарников на машине разработчика удобен `go-size-analyzer` (`gsa`). Это инструмент, а не зависимость проекта.

## 7. Проверка в CI

**`size-budget.txt`:**

```
# бинарник            тулчейн  байт     # почему столько
examples/hello        tinygo   65536    # цель goals.md
examples/form         tinygo   163840   # оценка, уточнить в фазе 2
examples/logger       tinygo   256000   # цель goals.md
examples/hello        gc       0        # заполнить по итогам S1 (замер + 10 %)
```

**`tools/sizecheck.sh`:**
1. собирает каждый пример нужным тулчейном с релизными флагами;
2. сравнивает размер с бюджетом;
3. печатает таблицу «бюджет / факт / запас»;
4. при превышении возвращает код ≠ 0.

Если размер **уменьшился** больше чем на 10 %, скрипт напоминает снизить бюджет, чтобы запас не «съели» незаметно.

**`tools/depcheck.sh`:**

```sh
for os in linux windows; do
  GOOS=$os CGO_ENABLED=1 go list -f '{{.ImportPath}} {{join .Imports " "}}' . ./internal/... |
  # каждое импортируемое имя должно быть в белом списке или начинаться с nui/internal/
  …
done
```

Проверяется **только не-тестовый** код: `.Imports`, а не `.TestImports`.
