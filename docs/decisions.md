# Архитектурные решения (ADR)

Каждое решение записано в одном формате: **контекст → решение → что отвергли → цена → где соблюдается**. Чтобы изменить решение, нужно добавить новый ADR, который отменяет старый, а не тихо отступить от него в коде.

---

## ADR-1. Нативные виджеты ОС

**Контекст.** Есть два пути: рисовать виджеты самим (Fyne, Gio, Flutter) или вызывать виджеты ОС (libui, SWT, wxWidgets). При собственной отрисовке приходится заново писать ввод текста, IME (китайский, японский, ввод через ibus), доступность для экранных дикторов, буфер обмена, HiDPI, перенос строк с шейпингом (HarfBuzz) и поддержку Wayland/X11. На это уходят годы, а бинарник растёт на мегабайты.

**Решение.** Используем только виджеты ОС: GTK3 на Linux, Win32 (comctl32) на Windows, AppKit на macOS (необязательно).

**Отвергнуто:**
- собственная отрисовка: размер, объём работы, «чужой» вид;
- webview: тяжёлая зависимость, двойной стек.

**Цена.** Доступен только наименьший общий знаменатель виджетов. Поведение на разных ОС различается в мелочах. Всё нестандартное придётся рисовать через `Canvas` (фаза 6).

**Где соблюдается.** Набор виджетов в [api.md](api.md) включает только то, что есть во всех целевых ОС.

## ADR-2. GTK3, а не GTK4

**Контекст.** На Linux «нативным» тулкитом фактически считается GTK, а Qt вызвать без обёртки на C++ нельзя. В Debian 12 стоит GTK 4.8: в нём нет `GtkFileDialog` (он появился в 4.10), а `GtkFileChooserNative` объявлен устаревшим. GTK3 3.24 есть и в Debian 12, и в Debian 13, а также во всех живых дистрибутивах.

**Решение.** Драйвер для Linux пишем на GTK3 (≥ 3.22).

**Отвергнуто:**
- GTK4: другая модель (нет `gtk_main`, асинхронные диалоги, нет `show_all`), а в Debian 12 его не хватает;
- Qt: C++ ABI.

**Цена.** GTK3 находится в режиме поддержки, новых возможностей в нём не будет. Драйвер для GTK4 можно добавить позже за тем же контрактом драйвера ([driver-gtk3.md](driver-gtk3.md)). Публичный API от этого не изменится.

**Где соблюдается.** [driver-gtk3.md](driver-gtk3.md): все функции из списка есть в GTK 3.22.

## ADR-3. FFI: cgo с собственными прототипами, без системных заголовков

**Контекст.** Вызвать C из Go можно тремя способами:

1. cgo с `#include <gtk/gtk.h>`. Нужен `libgtk-3-dev`, а TinyGo пришлось бы разбирать через libclang тысячи строк заголовков GTK. Это медленно и хрупко.
2. purego (dlopen без cgo). Работает только с gc: purego опирается на внутренности рантайма gc и на ассемблер, в TinyGo его нет.
3. cgo, в преамбуле которого объявлены **только нужные нам функции** собственными прототипами.

**Решение.** Используем вариант 3.

- Файл `internal/drv/gtk3_linux.h` объявляет непрозрачные типы (`typedef struct _GtkWidget GtkWidget;`) и около 100 прототипов.
- Линкуемся по soname: `-l:libgtk-3.so.0`. Для этого достаточно runtime-пакета, `-dev` не нужен.
- Всё, что Go не может вызвать напрямую, уходит в маленькие C-функции `nui_*` в `wrap_linux.c`: макросы (`g_signal_connect`), функции с переменным числом аргументов (`gtk_message_dialog_new`), структуры на стеке (`GtkTextIter`) и `GVariant`.
- Go видит только указатели, целые числа, `double` и строки.

**Отвергнуто:** варианты 1 и 2 по причинам выше.

**Цена:**
- Нужен C-компилятор (gcc для gc; у TinyGo свой clang).
- Ошибка в прототипе — это неопределённое поведение. Защита: `make check-protos` компилирует наши прототипы вместе с настоящим `<gtk/gtk.h>` и сверяет типы. Эта проверка требует `libgtk-3-dev`, но только в CI ([driver-gtk3.md](driver-gtk3.md), раздел «Проверка прототипов»).
- Кросс-компиляция под Windows требует mingw.

**Где соблюдается.** [driver-gtk3.md](driver-gtk3.md), [testing.md](testing.md) (`check-protos`).

## ADR-4. Два тулчейна: TinyGo для релиза, gc для разработки и как запасной релиз

**Контекст.**
- Цель по размеру — ≤ 250 КБ ([goals.md](goals.md)). Рантайм gc весит около 1 МБ, значит, цель достижима только с TinyGo.
- Но на Linux TinyGo статически линкует собственную musl, а системный GTK тянет glibc. Две libc в одном процессе несовместимы: они конфликтуют за указатель потока (TLS), и программа падает.
- Обойти это должен [TinyGo PR #5838](https://github.com/tinygo-org/tinygo/pull/5838): флаг `-libc=glibc`, динамическая линковка с системной glibc. Автор PR проверил его на SDL2. На 07.10.2026 PR **открыт**.

**Решение:**
- Весь код nui обязан собираться **и gc, и TinyGo**.
- **gc** нужен для разработки (быстрая сборка, `-race`, отладчик delve, `go test`) и как **запасной релизный** тулчейн.
- **TinyGo с `-libc=glibc`** — релизный тулчейн. Он становится им после того, как спайк S2 ([roadmap.md](roadmap.md)) подтвердит, что связка работает: на ветке PR, на релизе с влитым PR или со своим target-файлом (спайк S3).

**Отвергнуто:**
- «Только gc»: не достигается цель по размеру.
- «Только TinyGo»: сейчас это блокирует разработку на открытом PR, а без gc нет `-race` и delve.

**Цена:**
- Каждое правило кода проверяется на совместимость с TinyGo. В ядре нет `reflect` и `fmt`, есть ограничения на горутины (ADR-7).
- CI собирает обоими тулчейнами.
- Если S2 провалится, релиз до слияния PR будет весить около 1,5 МБ (с UPX — около 0,6 МБ).

**Если S2 и S3 провалятся** и релизным останется gc:
- Правила кода библиотеки (белый список импортов, ядро без горутин, дисциплина DCE) **остаются**. Они почти ничего не стоят, уменьшают и gc-сборку и держат путь TinyGo открытым до слияния PR.
- Экономия на стороне приложения ([acceptance.md](acceptance.md), §5: C-хелперы для времени, свои `itoa` и `fmtSize`) становится **необязательной**. Под gc пол рантайма около 1 МБ, и `time` со `strconv` его заметно не меняют. Логгер для gc можно писать на `time` и `strconv`, бюджет — строки gc в [size.md](size.md).
- `size-budget.txt` получает цифры S1, а TinyGo-задачи в CI становятся «можно падать».

**Статус (08.10.2026): подтверждено спайком S3**, но без PR: выпущенный TinyGo 0.42.0 со своим target-файлом проходит все критерии S2, спайк весит 35 952 байта. Как именно — ADR-17.

**Где соблюдается.** [size.md](size.md), [build.md](build.md), [testing.md](testing.md) (матрица CI).

## ADR-5. Драйвер выбирается при компиляции: один пакет `internal/drv`, файлы по ОС

**Контекст.** Если сделать драйвер через Go-интерфейс (`type Driver interface { ... 80 методов }`), компилятор не сможет выбросить неиспользуемые методы. Вызов через интерфейс держит в бинарнике все реализации, а вместе с ними и их C-вызовы. Для 250 КБ это недопустимо.

**Решение.** `internal/drv` — один Go-пакет. Реализации лежат в файлах с суффиксом ОС: `*_linux.go`, `*_linux.c`, `*_linux.h`, `*_windows.go` и т. д. Набор функций в обоих вариантах одинаковый; это и есть **контракт драйвера** ([driver-gtk3.md](driver-gtk3.md), раздел «Контракт драйвера»). Пакет `nui` вызывает `drv.LabelSetText(...)` как обычную функцию. Если в каком-то драйвере функции не хватает, сборка под эту ОС падает с ошибкой компиляции, а это и есть нужная проверка.

**Отвергнуто:**
- Интерфейс Driver: мешает DCE.
- Два пакета `internal/gtk3` и `internal/win32` с выбором импорта по тегам: импорт в Go действует на один файл, поэтому понадобились бы обёртки-переходники для каждой функции.

**Цена.** Нельзя переключить драйвер во время работы, например выбрать GTK3 или GTK4. Это нам и не нужно: выбор делается тегом сборки.

**Где соблюдается.** [architecture.md](architecture.md), раздел «Пакеты».

## ADR-6. Связь C ↔ Go только через числовые id и 4 трамплина

**Контекст:**
- По правилам cgo C не может хранить Go-указатели. Сборщик TinyGo консервативный и не сканирует память C. Если Go-объект доступен только через указатель, лежащий в C, его освободят.
- `purego.NewCallback` и `syscall.NewCallback` ограничены примерно 2000 колбэков на процесс.

**Решение:**
- Каждый объект nui (виджет, таймер, наблюдатель за fd) регистрируется в `internal/core`. Реестр — это срез `[]Receiver` и стек свободных слотов, объект получает `id uint32`; id 0 зарезервирован.
- В C уходит только `user_data = id<<5 | kind`, где kind — тип события, 5 бит.
- В обратную сторону ведут 4 экспортированные Go-функции («трамплины»), по одной на каждую сигнатуру колбэка: сигнал без результата, сигнал с результатом, источник GLib, fd-источник. Все они вызывают `core.Dispatch(ud, arg)`.

**Отвергнуто:**
- Отдельный колбэк на каждый виджет: лимиты, утечки.
- Хранить Go-указатели в `g_object_set_data`: запрещено правилами cgo и опасно со сборщиком TinyGo.

**Цена.** Лишний поиск по срезу при каждом событии, это наносекунды. Ещё одно ограничение: не больше 2²⁷ одновременно живых объектов.

**Уточнение (List, 09.10.2026).** Своей модели `GtkTreeModel` нужен текст ячейки в момент отрисовки — это не событие, а вопрос к данным. Для неё ещё два экспорта: `nuiListCell` и `nuiListDrop`. Правило то же: в C лежит только номер модели, функции ячеек — в Go-карте, запись удаляется при уничтожении модели.

**Где соблюдается.** [runtime.md](runtime.md), разделы «Реестр» и «Трамплины».

## ADR-7. Ядро без горутин; `Do` — мост для приложений с горутинами

**Контекст:**
- GUI ОС однопоточный: всё делается в главном потоке.
- В TinyGo есть три планировщика: `none` (горутин нет вообще), `tasks` (кооперативный, один поток ОС), `threads` (потоки ОС; на Linux он появился недавно).
- При `tasks` поток, сидящий в `gtk_main`, не отдаёт управление, и горутины не выполняются.

**Решение:**
- Ядро nui не запускает ни одной горутины и не использует каналы.
- Таймеры (`After`, `Every`) и ожидание fd (`Watch`) построены на источниках GLib (`g_timeout_add`, `g_unix_fd_add`). Приложение, которое работает только с ними, можно собрать с `-scheduler=none`, и это самый маленький вариант.
- `nui.Do(fn)` — потокобезопасный мост: очередь под `sync.Mutex` плюс `g_idle_add`. Он для приложений с горутинами: при сборке gc или TinyGo с `-scheduler=threads`.
- Режим TinyGo `-scheduler=tasks` **не поддерживается** вместе с горутинами в приложении.

**Отвергнуто.** Крутить цикл GLib из Go неблокирующими итерациями и вызывать `runtime.Gosched()` между ними. Это активное ожидание: процессор занят постоянно, а таймеры Go всё равно не разбудят заблокированный поток.

**Цена.** Автор приложения должен знать матрицу режимов ([runtime.md](runtime.md), раздел «Режимы планировщика TinyGo»).

**Где соблюдается:**
- `make deps` запрещает импорт `time`, а ревью — слово `go` в пакетах `nui` и `internal/*`;
- [runtime.md](runtime.md).

## ADR-8. Семантика обработчиков событий

**Решение:**
1. Обработчики `On*` вызываются **только в ответ на действия пользователя**. Вызов `Set*` из кода их **не** запускает: `entry.SetText("x")` не вызовет `OnChange`. Так не бывает циклов «обработчик → Set → обработчик», и логику проще читать. Это относится к любому программному изменению, а не только к `Set*`: `Add`, `Clear` и `Append` тоже не вызывают обработчиков.
2. **На событие — один обработчик.** Повторный `OnClick(fn)` заменяет предыдущий, `OnClick(nil)` снимает его. Списков подписчиков нет.
3. **Сигнатура почти всегда `func()`.** Значение обработчик читает геттером: `slider.Value()`. Исключение — `Window.OnClose(func() bool)`: функция возвращает, можно ли закрыть окно.
4. Обработчики всегда выполняются в UI-потоке.
5. Число вызовов на одно действие не гарантируется: GTK может прислать два сигнала (например, удаление и вставку при вставке поверх выделения). Обработчик читает значение геттером и не считает вызовы.

**Отвергнуто:**
- Обработчики с аргументами разных типов: больше кода и больше типов, а значит, больше размер.
- Списки подписчиков: на практике почти не нужны.
- События и на программные изменения: в нативных тулкитах это источник бесконечных циклов.

**Цена.** Если приложению нужно отреагировать на собственный `SetText`, оно вызывает свою функцию явно.

**Где соблюдается.** [runtime.md](runtime.md), раздел «Тихий режим»; интеграционные тесты в [testing.md](testing.md).

## ADR-9. Паника в обработчике завершает процесс

**Решение.** nui не делает `recover` в трамплинах. Паника в обработчике завершает процесс:
- gc печатает стек;
- TinyGo с `-panic=print` печатает сообщение, а с `-panic=trap` сразу останавливает процесс (SIGILL).

**Почему так:**
- Перехватить панику и продолжить работу — значит оставить приложение в неизвестном состоянии.
- В TinyGo `recover` поддерживается не на всех целевых платформах и увеличивает размер.
- Принцип «падай сразу» (fail fast) честнее.

**Цена.** Приложение, которому нужна устойчивость, ставит `recover` в своих обработчиках само.

**Где соблюдается.** [runtime.md](runtime.md), раздел «Паники».

## ADR-10. Раскладка: эталон — контейнеры GTK, движок на Go только для Win32

**Контекст.** В GTK есть хорошие контейнеры (`GtkBox`, `GtkGrid`), а абсолютное позиционирование работает плохо: `GtkFixed` не даёт окну уменьшиться. В Win32 менеджеров раскладки нет вообще.

**Решение:**
- Публичная семантика раскладки маленькая: VBox/HBox (`Spacing`, `Padding`, `Expand`, `Stretch`) и Grid. Она описана в [layout.md](layout.md).
- На GTK она отображается на родные контейнеры, и **поведение GTK считается эталоном**.
- Для Win32 (фаза 5) пишется движок `internal/layout` на чистом Go. Его поведение сверяется golden-тестами с эталонными раскладками, снятыми с GTK.

**Отвергнуто:**
- Единый движок на Go для всех ОС: на GTK он воюет с самим GTK.
- Отдельная семантика для каждой ОС: приложение будет вести себя по-разному.

**Цена.** Два пути реализации, которые нужно держать одинаковыми. Помогают golden-тесты и сознательно маленькая семантика.

**Где соблюдается.** [layout.md](layout.md).

## ADR-11. Бюджет размера — это правило кода

**Решение:**
- Пакеты `nui` и `internal/*` импортируют только стандартные пакеты из белого списка: `unsafe`, `sync`, `sync/atomic`, `errors`, `runtime`, `unicode/utf8`, `unicode/utf16` (только Windows) и `C`.
- В `go.mod` нет `require`.
- Размер примеров проверяется в CI по `size-budget.txt`. Превышение роняет сборку, а поднять бюджет можно только отдельным коммитом с обоснованием.

**Отвергнуто.** «Сначала сделаем, потом ужмём»: так `fmt` и `reflect` проникают повсюду, и вычистить их потом уже нельзя.

**Цена.** Внутри ядра нет `fmt.Sprintf`, `strconv` и `time`. Немногие нужные вещи пишутся вручную, например перевод числа в строку для отладочных сообщений.

**Где соблюдается.** [size.md](size.md); `make deps`, `make size`.

## ADR-12. Динамическая линковка на этапе сборки, без dlopen

**Решение.** Библиотеки GTK указываются линковщику (`-l:libgtk-3.so.0` и т. д.), и загрузчик ОС подключает их при старте программы.

**Отвергнуто.** Самостоятельный `dlopen` с таблицей указателей на функции. Он дал бы понятное сообщение «GTK не найден» и выбор между GTK3 и GTK4 во время работы, но обошёлся бы в сотню переходников и лишний слой.

**Цена.** Если GTK3 не установлен, программа не запускается и выдаёт системную ошибку: `error while loading shared libraries: libgtk-3.so.0`. Это закрывается зависимостью в пакете: `Depends: libgtk-3-0 | libgtk-3-0t64`.

**Где соблюдается.** [driver-gtk3.md](driver-gtk3.md), раздел «Линковка». Единственное исключение — `TaskDialog` на Windows (ADR-16).

## ADR-13. Строки передаются в C через Go-память на время вызова

**Решение.**
- Строка Go копируется в Go-срез `[]byte` с завершающим нулём, и C получает указатель на него только **на время вызова**. GTK копирует все строки, которые сохраняет, поэтому `malloc`/`free` и `C.CString` не нужны.
- Строки, которые возвращает C, сразу копируются в Go. Если они принадлежат вызывающему (`gchar*`, который «надо освободить»), после копирования вызывается `g_free`.

**Почему так:**
- Одинаково работает в gc и TinyGo.
- Нет утечек и забытых `free`.
- Правила cgo разрешают такие указатели: память Go без вложенных Go-указателей, C её не сохраняет.

**Цена.** Строка обрезается на первом байте `\x00`. Кроме того, при копировании невалидные последовательности UTF-8 заменяются на U+FFFD: GTK невалидный UTF-8 не принимает — пишет `Gtk-CRITICAL` и ничего не делает. Пути файловой системы копируются без замены (`cpath`). Всё это фиксируется в [api.md](api.md).

**Где соблюдается.** [runtime.md](runtime.md), раздел «Строки».

## ADR-14. Видимость и завершение программы

**Решение:**
1. Виджеты становятся видимыми сразу при создании (`gtk_widget_show`), окна — только после `Show()`. `gtk_widget_show_all` не используется: он отменил бы `SetVisible(false)`, сделанный до показа окна.
2. ~~Когда число живых окон падает с 1 до 0, nui сам вызывает `Quit()`, и `Run` возвращает управление.~~ **Заменён ADR-15.**
3. `Window.Close()` из кода закрывает окно без вызова `OnClose` (по ADR-8: это не действие пользователя).

**Где соблюдается.** [runtime.md](runtime.md), разделы «Run и Quit» и «Жизненный цикл».

## ADR-15. Автовыход, когда не осталось видимых окон (заменяет ADR-14, п. 2)

**Контекст.** По ADR-14 программа завершалась, когда число **живых** окон падало до нуля. Но окно, созданное заранее и ещё не показанное (например, «О программе»), тоже живое. Тогда после закрытия главного окна процесс продолжает работать без единого видимого окна, и пользователь не может его закрыть.

**Решение.** Когда окно уничтожается, nui проверяет оставшиеся живые окна. Если ни одно из них не видимо, вызывается `Quit()`. `Hide()` сам выход не вызывает: проверка делается только при уничтожении окна.

**Отвергнуто:**
- Счёт живых окон (ADR-14): скрытое окно держит процесс.
- Выход и при `Hide()` последнего видимого окна: ломает сценарий «спрятать окно и показать его по таймеру».
- Флаг вроде `SetQuitOnClose`: лишнее имя в API ради редкого случая.

**Цена.** Программа не продолжит работу, если её видимое окно уничтожено, а остались только скрытые. Кому это нужно, перехватывает закрытие в `OnClose`: прячет окно через `Hide()` и возвращает `false`.

**Где соблюдается.** [runtime.md](runtime.md), разделы «Run и Quit» и «Жизненный цикл»; [api.md](api.md), §1 и §5.

## ADR-16. `TaskDialog` на Windows ищется через `GetProcAddress` (исключение из ADR-12)

**Контекст.**
- `TaskDialog` есть только в Common Controls v6. Статические импорты Windows разрешает при загрузке exe. Если у приложения нет манифеста v6, подключается comctl32 v5, где этой функции нет, и программа **не запускается** с ошибкой «точка входа не найдена».
- Запасной путь из [driver-win32.md](driver-win32.md), §8 (`CreateActCtxW` в `Init`) не помогает: он срабатывает уже после разрешения импортов.
- Манифест — свойство приложения, а подхватит ли TinyGo `.syso`, выяснится только в спайке S4.

**Решение.** При первом вызове `Message`, `Alert` или `Ask` драйвер вызывает `LoadLibraryW(L"comctl32.dll")` и `GetProcAddress(…, "TaskDialog")`. К этому моменту `Init` уже активировал контекст с v6. Если функция нашлась, используется она, если нет — `MessageBoxW`.

**Отвергнуто:**
- Статический импорт и обязательный манифест: без манифеста exe не запускается вовсе, а библиотека не может гарантировать манифест приложения.
- Только `MessageBoxW`: нет крупного заголовка и пояснения под ним, вид хуже.

**Цена.** Один динамический поиск функции и около 20 строк в драйвере. Остальные функции Win32 импортируются статически, как требует ADR-12.

**Уточнение после S4 (09.10.2026).** Динамически грузится вся comctl32, в том числе `InitCommonControlsEx`. Статический импорт загрузил бы её при старте, раньше, чем драйвер включит контекст с v6, и у exe без манифеста осталась бы v5. Поэтому у exe нет зависимости от comctl32 вовсе. TinyGo подхватывает манифест через `-l:rsrc.o` ([spike/s4/RESULT.md](../spike/s4/RESULT.md)), а запасной контекст из `shell32.dll` под Wine v6 не включил.

**Где соблюдается.** [driver-win32.md](driver-win32.md), §8 и §9.

## ADR-17. TinyGo: выпущенная версия + свой target-файл вместо `-libc=glibc` (уточняет ADR-4)

**Контекст.**
- ADR-4 делал малую сборку зависимой от [TinyGo PR #5838](https://github.com/tinygo-org/tinygo/pull/5838) (флаг `-libc=glibc`), а он на 08.10.2026 не влит.
- Разбор PR показал: он меняет только сборку (выбор libc, флаги линковщика, startup-объекты glibc), но не рантайм и не компилятор.
- Спайк S3 ([spike/s3/RESULT.md](../spike/s3/RESULT.md)) выразил всё это target-файлом для **выпущенного** TinyGo. Спайк проходит все критерии S2, вариант без планировщика весит 35 952 байта.

**Решение.**
- Малая сборка — выпущенный TinyGo (проверено на 0.42.0) с target-файлом nui `targets/linux-glibc-<arch>.json`:
  - `libc` пустая — своя musl не собирается;
  - триплет `<arch>-unknown-linux-gnu`;
  - заголовки glibc для C-файлов рантайма TinyGo — через `-isystem`;
  - линковка встроенным `ld.lld`: `crt1.o`, `crti.o`, `crtn.o`, `-lc`, `-L/usr/lib/<multiarch>`, `--dynamic-linker`; с 12.10.2026 и `-l:libm.so.6` — для `math.Sin` и других функций, которые TinyGo отдаёт libm (без неё — «linker could not find symbol sin»).
- Файлы целей лежат в репозитории nui, по одному на архитектуру. Makefile передаёт `-target=targets/linux-glibc-$(ARCH).json`.
- Когда PR #5838 вольют, переход на `-libc=glibc` — отдельный ADR. Он сократит target-файл, но кода nui не коснётся.

**Отвергнуто:**
- Ждать слияния PR: малая сборка заблокирована на неопределённый срок.
- Собирать TinyGo из ветки PR: сборка вместе с LLVM, у каждого разработчика свой тулчейн.
- `"linker": "cc"` в target-файле (системный gcc сам подставил бы glibc): TinyGo 0.42 требует `ld.lld`.

**Цена.**
- Target-файл повторяет встроенную цель TinyGo (`compileopts/target.go`). При обновлении TinyGo его надо сверять с ней: новые `extra-files`, флаги. Сверку ловит selftest TinyGo в CI.
- Нужен `libc6-dev` с заголовками glibc — он и так входит в `build-essential`.
- `crtn.o` стоит не последним (флаги цели идут до объектов). Это безопасно, пока ни один объект не добавляет секцию `.init`; подробности — в spike/s3/RESULT.md.

**Где соблюдается.** [build.md](build.md), §3–4; [size.md](size.md), §4; [spike/s3](../spike/s3/).

## ADR-18. Эталон раскладки снимает сам драйвер nui на GTK (уточняет ADR-10)

**Контекст.**
- layout.md, §8 предполагал отдельный генератор golden-файлов: деревья из «голых» контейнеров GTK и листья-подкласс `GtkWidget` с заданными минимальным и естественным размерами. Для подкласса нужен `libgtk-3-dev`, а в остальном nui обходится без него (ADR-3).
- Такой генератор проверял бы, что движок повторяет GTK, но не то, что nui на GTK ведёт себя так, как обещает layout.md: флаги `hexpand`/`vexpand`, `Stretch`, `ExpandCol` проставляет драйвер, и ошибка в нём прошла бы мимо.

**Решение.**
- Случаи (`internal/layout/testdata/cases`) строятся из **настоящих виджетов nui** интеграционным тестом `TestLayoutGTK` (тег `gui`). GTK раскладывает окно, тест снимает с GTK минимальные и естественные размеры всех узлов и их прямоугольники.
- Листья не обязаны иметь заданные размеры: размеры листьев — **вход** движка, их тест берёт у GTK. Сравниваются прямоугольники всех узлов и размеры контейнеров. Поэтому сверка не зависит от шрифтов и идёт на любой машине с GTK — прямо в `make test`.
- Снимки (`testdata/golden`) пишет `make golden` в контейнере `nui-bookworm`. Чистый Go-тест `TestGolden` сверяет с ними движок без GTK — так golden-тесты пройдут и на Windows.
- Оформление `Frame` и `Scroll` (`Inset`) и их собственный минимум (`Floor`: ширина заголовка, полосы прокрутки) — тоже вход движка. Его измеряет драйвер, а на GTK — тест.

**Отвергнуто:**
- Отдельный генератор с подклассом `GtkWidget`: нужен `libgtk-3-dev`, не проверяет драйвер.
- Только «прямоугольники с заданными размерами» (`GtkDrawingArea`): не покрывают листья, у которых минимум меньше естественного, а это и есть самая хитрая часть (нехватка места).

**Цена.**
- Снимки зависят от шрифтов и темы контейнера. При смене образа их перегенерируют, а изменения разбирают отдельно.
- Оформление `Frame` и `Scroll` тест вычисляет по месту ребёнка, поэтому у ребёнка в случаях выравнивание `fill`.

**Где соблюдается.** [layout.md](layout.md), §8; `layout_gui_test.go`; `internal/layout/golden`.

## ADR-19. Небольшой набор оформления: цвет, фон, размер шрифта (меняет нецель из goals.md)

**Контекст.**
- goals.md исключал стили: внешний вид даёт ОС, исключение — жирный шрифт и цвет у `Label`.
- На реальном интерфейсе (боковое меню, чат, строка состояния) зоны сливаются: рамок, разделителей и отступов не хватает. Пользователь выбрал фон контейнеров, размер шрифта подписей и цвета полей и кнопок (09.10.2026).

**Решение.**
- Цвет текста и фон — точечно, у тех виджетов, где это разделяет зоны: `Window`, `Box`, `Grid` (только фон), `Label`, `Button`, `Entry`, `TextView`, `Chat`; размер шрифта — у `Label` (`SetFontScale`, относительно шрифта системы). У остальных (Combo, Slider, Progress, Check) — нет.
- Контракт драйвера: `SetForeground(h, color)`, `SetBackground(h, color, panel)`, `LabelSetFontScale(h, pct)`.
- **GTK:** свой `GtkCssProvider` на виджет (приоритет APPLICATION), состояние — в данных объекта, у Go-структур nui полей не прибавилось. Отступ `border-width` у GTK лежит вне фона, поэтому у цветных Box и Grid (`panel`) он становится CSS `padding`: раскладка детей та же, отступ закрашен. Шрифт подписи — атрибут Pango `scale`.
- **Win32:** Box и Grid без HWND — их фон (вместе с отступом) рисует `WM_ERASEBKGND` окна или прокрутки. Подписи, флажки, ползунки и рамки берут фон ближайшей цветной панели (`WM_CTLCOLORSTATIC`), поля — только свой (`WM_CTLCOLOREDIT`). Цветную кнопку визуальный стиль Windows не перекрашивает, поэтому она становится `BS_OWNERDRAW` и рисуется драйвером: плоская заливка, рамка, текст, нажатие, фокус, кнопка по умолчанию. Шрифт подписи — свой `HFONT` из шрифта окна, пересоздаётся при смене dpi.

**Отвергнуто:**
- Темы и CSS в API: другая библиотека, другой размер и поведение на Windows.
- `SetBackground` у всех виджетов: у комбобокса, ползунка, индикатора Win32 не даёт честного способа.
- Наследование цвета текста от панели: на GTK цвет наследуется, на Win32 — нет; явный цвет у каждой подписи предсказуемее.

**Цена.**
- Цвета не следуют за тёмной темой ОС.
- Цветная кнопка на Windows выглядит плоской, без визуального стиля системы.
- Около 500 строк в драйверах вместе с прототипами; программы, которые оформление не используют, не растут.

**Где соблюдается.** [api.md](api.md), §4 («Цвет и фон»); [goals.md](goals.md), «Нецели»; driver-gtk3.md, §3; driver-win32.md, §10.

## ADR-20. Картинки декодирует ОС

**Контекст.**
- Нужна картинка в интерфейсе: логотип, превью выбранного файла, ответ ИИ с изображением.
- Декодеры Go (`image/png`, `image/jpeg`) добавили бы к бинарнику TinyGo десятки килобайт и не проходят белый список импортов (ADR-7).
- Обе ОС уже умеют декодировать: GdkPixbuf входит в зависимости GTK, GDI+ есть в каждой Windows начиная с XP.

**Решение.**
- `Image` получает байты файла (`SetData`) или путь (`SetFile`, файл читает драйвер: у nui нет пакета `os`). Форматы, обещанные на всех ОС: PNG, JPEG, GIF (первый кадр), BMP.
- Размер — в логических пикселях. Драйвер хранит байты файла и рисует картинку под масштаб экрана из исходных точек: на HiDPI она чёткая. При смене масштаба картинка перерисовывается из байтов, а полноразмерная декодированная копия не хранится.
- `SetFit(w, h)` только уменьшает картинку с сохранением пропорций; расчёт — `core.Fit`, общий для ОС.
- **GTK:** `GdkPixbufLoader`, `gdk_pixbuf_apply_embedded_orientation`, cairo-поверхность с масштабом экрана, `gtk_image_set_from_surface`. Библиотеки libgdk-3, libgdk_pixbuf-2.0 и libcairo попадают в `NEEDED` только у программ с `Image` (`--as-needed`).
- **Win32:** `gdiplus.dll` загружается при первой картинке (`LoadLibraryW` + `GetProcAddress`, как comctl32 в ADR-16). Контрол — `STATIC` с `SS_OWNERDRAW`, рисует `GdiAlphaBlend` из DIB с умноженной альфой. EXIF-поворот JPEG читает Go (`core.Orientation`): GDI+ сам картинку не поворачивает, а Wine и тега не отдаёт.

**Отвергнуто:**
- Декодеры Go: размер и белый список импортов.
- WIC на Windows: тот же результат, но COM-интерфейсы в C — втрое больше кода.
- Растягивание картинки под размер места: на GTK3 у `GtkImage` нет такого режима, пришлось бы рисовать самим. Размер задаёт `SetFit`.

**Цена.**
- Набор форматов зависит от ОС сверх обещанных четырёх: на Linux может открыться SVG или WebP, на Windows — TIFF и ICO.
- Анимированный GIF показывается первым кадром.
- При загрузке и смене масштаба картинка декодируется целиком: фото на 12 Мп кратковременно занимает около 48 МБ.

**Где соблюдается.** [api.md](api.md), §19; driver-gtk3.md, §7; driver-win32.md, §5.
