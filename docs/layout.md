# Раскладка

Цель — **одинаковое поведение** на всех ОС при сознательно маленькой семантике. Эталон поведения — GTK (ADR-10). Здесь описано, что обещает nui, как это ложится на GTK и как это повторяет движок для Win32.

## 1. Модель

- Интерфейс — дерево. В узлах стоят контейнеры (`Box`, `Grid`, `Frame`, `Scroll`, `Window`), в листьях — виджеты.
- У каждого узла два размера по каждой оси:
  - **минимальный** — меньше нельзя, интерфейс сломается;
  - **естественный** — сколько виджет хочет, чтобы всё было видно.
- Родитель **измеряет** детей снизу вверх, затем **раздаёт** им прямоугольники сверху вниз.
- Скрытые виджеты (`SetVisible(false)`) не занимают места, и вокруг них не ставится `Spacing`.
- Внутри выделенной ячейки виджет располагается по `SetAlign(h, v)`:
  - `AlignFill` (по умолчанию) — занимает всю ячейку по этой оси;
  - `Start`, `Center`, `End` — получает естественный размер и прижимается к началу, центру или концу ячейки.
- **Ограничение модели:** размеры по осям считаются независимо. В GTK у метки с переносом (`SetWrap`) и у TextView с переносом высота зависит от выделенной ширины (height-for-width). Движок Win32 этого не повторяет и берёт для таких виджетов фиксированную оценку ([driver-win32.md](driver-win32.md), §6), а golden-тесты их не сравнивают.

## 2. Значения по умолчанию

| Что | Значение |
|---|---|
| `Box.Spacing` | 6 |
| `Box.Padding` | 0 |
| `Grid.Spacing` | 6 по колонкам, 6 по строкам |
| `Grid.Padding` | 0 |
| `Window.SetPadding` | 12 |
| `SetAlign` у виджетов | `AlignFill, AlignFill` |
| Выравнивание текста `Label` | Start |

6 и 12 — шаг сетки из GNOME HIG. С этими значениями формы выглядят аккуратно без всякой настройки.

## 3. Box (VBox / HBox)

**Главная ось** — вертикальная у VBox, горизонтальная у HBox.

1. Каждому видимому ребёнку выдаётся его естественный размер по главной оси.
2. `свободно = доступно − Σестественных − Spacing·(n−1) − 2·Padding`.
3. **Если свободное место есть (> 0)**, оно делится **поровну** между детьми, помеченными `Expand(...)`, и вставками `Stretch()`. Остаток от деления раздаётся по 1 px первым из них. Если растягиваемых нет, свободное место остаётся **в конце**.
4. **Если места не хватает (< 0)**, каждый ребёнок получает не меньше своего минимума. Остаток сверх минимумов распределяется по алгоритму GTK (`gtk_distribute_natural_allocation`): сначала полностью удовлетворяются дети с самым маленьким разрывом «естественный − минимальный», и место раздаётся равными долями с округлением **вверх**: доля = ⌈оставшееся место / число оставшихся детей⌉.
5. Меньше суммы минимумов окно не сжимается: и GTK, и Win32-драйвер ограничивают минимальный размер окна.

**Поперечная ось.** Каждый ребёнок получает всю поперечную ширину Box и располагается в ней по своему `SetAlign`.

**Размеры самого Box:**
- по главной оси — `Σ(размеров детей) + Spacing·(n−1) + 2·Padding`;
- по поперечной — `max(размеров детей) + 2·Padding`.

Это верно и для минимального, и для естественного размера.

**Растягивание не распространяется на родителей.** То, что внутри Box есть `Expand`, **не** делает сам Box растягиваемым в его родителе. Чтобы Box растягивался, пометьте его самого: `HBox(a, Expand(VBox(...)))`.

## 4. Grid

- Ячейка задаётся как `(col, row)` с размером `cols × rows` (по умолчанию 1×1). Нумерация с 0.
- **Ширина колонки** — максимум естественных ширин ячеек, которые занимают только эту колонку.
- **Ячейка на несколько колонок**, если ей не хватает места, добирает недостающее так же, как GTK (`gtk_grid_request_spanning`):
  - если среди её колонок есть растягиваемые (`ExpandCol`), недостающее делится **только между ними**, иначе — между всеми её колонками;
  - доли равные, с округлением вниз, а остаток достаётся последней из этих колонок;
  - так считаются и минимальная, и естественная ширина.

  Пример — форма логгера ([acceptance.md](acceptance.md), §2). `port` занимает колонки 1–2, растягивается колонка 2. Поэтому вся недостающая ширина `port` уходит в колонку 2, а колонка 1 остаётся шириной поля скорости.
- **Свободная ширина** делится поровну между колонками, помеченными `ExpandCol`. Если таких нет, свободное место остаётся справа.
- Нехватка места распределяется как в Box: правило 4 применяется к колонкам.
- Строки устроены так же, только по высоте и с `ExpandRow`.
- `Spacing(colGap, rowGap)` ставится между соседними **непустыми** колонками и строками. Пустые колонки и строки имеют нулевой размер. Если GTK ведёт себя иначе, верным считается GTK: это зафиксируют golden-тесты, а пункт будет исправлен.
- Внутри ячейки виджет располагается по `SetAlign`.

## 5. Window, Frame, Scroll

- **Window.** Содержимое занимает всю клиентскую область за вычетом `Padding`.
  - Минимальный размер окна = минимальный размер содержимого + 2·Padding.
  - `SetSize` для растягиваемого окна задаёт начальный размер, для нерастягиваемого — фиксированный (не меньше естественного размера содержимого). См. [api.md](api.md), §5.
- **Frame** добавляет рамку и заголовок. Её размер = размер ребёнка + оформление ОС.
- **Scroll.** Минимальный размер маленький (около 1–2 строк и полосы прокрутки), естественный равен естественному размеру ребёнка. Если места меньше, появляются полосы прокрутки.

## 6. Как это ложится на GTK

| nui | GTK3 |
|---|---|
| `VBox`/`HBox` | `gtk_box_new(GTK_ORIENTATION_VERTICAL/HORIZONTAL, spacing)` |
| `Box.Spacing(px)` | `gtk_box_set_spacing` |
| `Box.Padding(px)`, `Grid.Padding`, `Window.SetPadding` | `gtk_container_set_border_width` |
| ребёнок Box | `gtk_box_pack_start(box, child, expand, TRUE /*fill*/, 0)`; `expand` = флаг `Expand(...)` |
| `Stretch()` | пустой `gtk_box_new(…, 0)`, упакованный с `expand = TRUE` |
| `NewGrid` | `gtk_grid_new` |
| `Grid.Add/AddSpan` | `gtk_grid_attach(grid, child, col, row, cols, rows)` |
| `Grid.Spacing` | `gtk_grid_set_column_spacing`, `gtk_grid_set_row_spacing` |
| `ExpandCol(c)` | `gtk_widget_set_hexpand(child, TRUE)` у детей, занимающих **только** колонку c (1×N) |
| `ExpandRow(r)` | то же с `vexpand` |
| `SetAlign(h, v)` | `gtk_widget_set_halign/valign`. Наш `Align` → `GtkAlign`: Fill→FILL(0), Start→START(1), Center→CENTER(3), End→END(2) |
| `SetMinSize(w, h)` | `gtk_widget_set_size_request` |

**Ловушка — распространение hexpand/vexpand в GTK.**
- В GTK3 флаг `hexpand` у ребёнка «всплывает» к родителям, если у родителя флаг не задан явно.
- `GtkBox` учитывает его **вдобавок** к `expand` при упаковке.

Без мер предосторожности Grid с растягиваемой колонкой начал бы растягиваться внутри HBox, а это нарушает правило из §3. Поэтому:

> Драйвер **каждому** создаваемому виджету и контейнеру явно вызывает `gtk_widget_set_hexpand(h, FALSE)` и `gtk_widget_set_vexpand(h, FALSE)`. После этого флаг считается «заданным», и всплытие прекращается. `TRUE` ставят только `ExpandCol` и `ExpandRow` у детей Grid, и дальше этого Grid флаг не уходит.

`Grid` хранит на стороне Go множество растягиваемых колонок и строк и список детей с их координатами. Так `ExpandCol`, вызванный **после** `Add`, проставит флаг уже вставленным детям, а вызванный **до** `Add` — будущим.

## 7. Движок для Win32 (`internal/layout`, фаза 5)

Это чистый Go без cgo, он тестируется на любой машине.

```go
type Size struct{ W, H int }
type Rect struct{ X, Y, W, H int }

type Node struct {
	Kind     uint8   // Leaf, VBox, HBox, Grid, Frame, Scroll
	Visible  bool
	Expand   bool    // для Box-родителя
	HAlign, VAlign uint8
	Min, Nat Size    // Leaf: заполняет драйвер (измерение контрола); контейнеры: Measure
	Spacing, ColGap, RowGap, Padding int
	Col, Row, Cols, Rows int // для детей Grid
	ExpandCols, ExpandRows []bool
	Children []*Node
	Out      Rect    // результат Arrange
}

func Measure(n *Node)          // снизу вверх: Min, Nat контейнеров
func Arrange(n *Node, r Rect)  // сверху вниз: Out всех узлов
```

Алгоритм Box, главная ось (в точности §3):

```
vis := видимые дети
total := Σ nat(c) + spacing·(len(vis)−1)
free := avail − total
if free >= 0:
    ex := дети с Expand (Stretch — это Leaf с Expand и нулевыми размерами)
    if len(ex) > 0:
        each := free / len(ex); extra := free % len(ex)
        для каждого c из ex по порядку: size(c) = nat(c) + each + (1, если extra > 0; extra−−)
    иначе: size(c) = nat(c) для всех, остаток в конце
else:
    distribute(vis, avail − Σmin − spacing·(…))   // как gtk_distribute_natural_allocation
```

```
distribute(children, space):  // space ≥ 0 — место сверх минимумов
    size(c) = min(c) для всех
    отсортировать children по gap(c) = nat(c) − min(c) по возрастанию (стабильно)
    for i, c := range children:
        share := ceil(space / (len(children) − i))   // как в GTK: (space + k − 1) / k
        give := min(gap(c), share)
        size(c) += give; space −= give
```

Grid: сначала колонки (ширины по §4), затем строки, затем `Out` у каждой ячейки и `SetAlign` внутри неё.

Измерение листьев на Win32 и пересчёт по `WM_SIZE` и `WM_DPICHANGED` описаны в [driver-win32.md](driver-win32.md).

**Когда пересчитывать раскладку.** Узел помечается «грязным» в таких случаях:
- `WM_SIZE`;
- изменился текст, от которого зависит естественный размер (`SetText` у Label, Button, Check);
- `SetVisible`;
- `Add`;
- `SetMinSize`.

Пересчёт делается **один раз** на пачку изменений: первое изменение отправляет `PostMessage(WM_APP_RELAYOUT)`, повторные — нет.

## 8. Golden-тесты: эталон снимается с GTK

Цель — доказать, что `internal/layout` раскладывает так же, как GTK, без зависимости от шрифтов.

1. **Случаи.** Файлы `internal/layout/testdata/cases/*.txt` на простом текстовом языке:

   ```
   window 400x300 padding=12
   vbox spacing=6
     leaf a 100x20
     leaf b expand 50x20..200x20      # мин..естественный
     hbox
       leaf c 50x20
       stretch
       leaf d 80x30 align=end,center
     grid colgap=6 rowgap=6 expandcol=1
       leaf e @0,0 60x20
       leaf f @1,0 100x20
       leaf g @0,1 span=2x1 300x40
   ```

2. **Генератор** `internal/layout/golden/gen.go` работает только на Linux, с тегом `gui`, под `xvfb-run` и с `GTK_THEME=Adwaita` (тема влияет на рамки Frame и Scroll). Ему нужен `libgtk-3-dev`: подкласс GtkWidget (см. ниже) переопределяет поля `GtkWidgetClass`, а для этого нужны настоящие заголовки. Поэтому генератор живёт отдельно от драйвера и запускается только в CI:
   - строит это дерево из настоящих контейнеров GTK;
   - лист — это `GtkDrawingArea` с заданным размером. Пары «мин..естественный» с разными значениями моделируются листом, у которого переопределены `get_preferred_width/height`; это делает маленькая C-обёртка, создающая подкласс GtkWidget;
   - реализует окно заданного размера, прокачивает цикл событий и записывает `testdata/golden/<case>.txt`: строки вида `путь x y w h` для каждого узла.

3. **Тест** `layout_test.go`: строит то же дерево из `Node`, вызывает `Measure` и `Arrange` и сверяет все прямоугольники с golden-файлом **точно**. Расхождение в 1 px допускается только у случаев, явно помеченных `tolerance=1`, с комментарием, откуда оно берётся.

Golden-файлы хранятся в репозитории. Их перегенерируют при смене версии GTK или темы Adwaita в CI, и любые изменения разбираются отдельно.

Тесты и генератор могут импортировать что угодно, включая `fmt` и `strings`: в бинарник приложения они не попадают, а `make deps` проверяет только не-тестовый код.
