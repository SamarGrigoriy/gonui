# Раскладка

Цель — **одинаковое поведение** на всех ОС при сознательно маленькой семантике. Эталон поведения — GTK (ADR-10). Здесь описано, что обещает nui, как это ложится на GTK и как это повторяет движок для Win32.

## 1. Модель

- Интерфейс — дерево. В узлах стоят контейнеры (`Box`, `Grid`, `Frame`, `Scroll`, `Window`), в листьях — виджеты.
- У каждого узла два размера по каждой оси:
  - **минимальный** — меньше нельзя, интерфейс сломается;
  - **естественный** — сколько виджет хочет, чтобы всё было видно.
- Родитель **измеряет** детей снизу вверх, затем **раздаёт** им прямоугольники сверху вниз.
- Скрытые виджеты (`SetVisible(false)`) не занимают места, и вокруг них не ставится `Spacing`.
- Внутри выделенной ячейки виджет располагается по `SetAlign(h, v)`:
  - `AlignFill` (по умолчанию) — занимает всю ячейку по этой оси;
  - `Start`, `Center`, `End` — получает естественный размер и прижимается к началу, центру или концу ячейки.
- **Ограничение модели:** размеры по осям считаются независимо. В GTK у метки с переносом (`SetWrap`) и у TextView с переносом высота зависит от выделенной ширины (height-for-width). Движок Win32 этого не повторяет и берёт для таких виджетов фиксированную оценку ([driver-win32.md](driver-win32.md), §6), а golden-тесты их не сравнивают.

## 2. Значения по умолчанию

| Что | Значение |
|---|---|
| `Box.Spacing` | 6 |
| `Box.Padding` | 0 |
| `Grid.Spacing` | 6 по колонкам, 6 по строкам |
| `Grid.Padding` | 0 |
| `Window.SetPadding` | 12 |
| `SetAlign` у виджетов | `AlignFill, AlignFill` |
| Выравнивание текста `Label` | Start |

6 и 12 — шаг сетки из GNOME HIG. С этими значениями формы выглядят аккуратно без всякой настройки.

## 3. Box (VBox / HBox)

**Главная ось** — вертикальная у VBox, горизонтальная у HBox.

1. Каждому видимому ребёнку выдаётся его естественный размер по главной оси.
2. `свободно = доступно − Σестественных − Spacing·(n−1) − 2·Padding`.
3. **Если свободное место есть (> 0)**, оно делится **поровну** между детьми, помеченными `Expand(...)`, и вставками `Stretch()`. Остаток от деления раздаётся по 1 px первым из них. Если растягиваемых нет, свободное место остаётся **в конце**.
4. **Если места не хватает (< 0)**, каждый ребёнок получает не меньше своего минимума. Остаток сверх минимумов распределяется по алгоритму GTK (`gtk_distribute_natural_allocation`): сначала полностью удовлетворяются дети с самым маленьким разрывом «естественный − минимальный», и место раздаётся равными долями с округлением **вверх**: доля = ⌈оставшееся место / число оставшихся детей⌉.
5. Меньше суммы минимумов окно не сжимается: и GTK, и Win32-драйвер ограничивают минимальный размер окна.

**Поперечная ось.** Каждый ребёнок получает всю поперечную ширину Box и располагается в ней по своему `SetAlign`.

**Размеры самого Box:**
- по главной оси — `Σ(размеров детей) + Spacing·(n−1) + 2·Padding`;
- по поперечной — `max(размеров детей) + 2·Padding`.

Это верно и для минимального, и для естественного размера.

**Растягивание не распространяется на родителей.** То, что внутри Box есть `Expand`, **не** делает сам Box растягиваемым в его родителе. Чтобы Box растягивался, пометьте его самого: `HBox(a, Expand(VBox(...)))`.

## 4. Grid

- Ячейка задаётся как `(col, row)` с размером `cols × rows` (по умолчанию 1×1). Нумерация с 0.
- **Ширина колонки** — максимум естественных ширин ячеек, которые занимают только эту колонку.
- **Ячейка на несколько колонок**, если ей не хватает места, добирает недостающее так же, как GTK (`gtk_grid_request_spanning`):
  - если среди её колонок есть растягиваемые (`ExpandCol`), недостающее делится **только между ними**, иначе — между всеми её колонками;
  - доли равные, с округлением вниз, а остаток достаётся последней из этих колонок;
  - так считаются и минимальная, и естественная ширина.

  Пример — форма логгера ([acceptance.md](acceptance.md), §2). `port` занимает колонки 1–2, растягивается колонка 2. Поэтому вся недостающая ширина `port` уходит в колонку 2, а колонка 1 остаётся шириной поля скорости.
- **Свободная ширина** делится поровну между колонками, помеченными `ExpandCol`. Если таких нет, свободное место остаётся справа.
- Нехватка места распределяется как в Box: правило 4 применяется к колонкам.
- Строки устроены так же, только по высоте и с `ExpandRow`.
- `Spacing(colGap, rowGap)` ставится между соседними **непустыми** колонками и строками. Пустые колонки и строки имеют нулевой размер. Если GTK ведёт себя иначе, верным считается GTK: это зафиксируют golden-тесты, а пункт будет исправлен.
- Внутри ячейки виджет располагается по `SetAlign`.

## 5. Window, Frame, Tabs, Scroll

- **Window.** Содержимое занимает всю клиентскую область за вычетом `Padding`.
  - Минимальный размер окна = минимальный размер содержимого + 2·Padding.
  - `SetSize` для растягиваемого окна задаёт начальный размер, для нерастягиваемого — фиксированный (не меньше естественного размера содержимого). См. [api.md](api.md), §5.
- **Frame** добавляет рамку и заголовок. Её размер = размер ребёнка + оформление ОС.
- **Tabs** (вид `Stack` движка) — как GtkNotebook: оформление ОС (ярлыки и рамка) плюс самая большая из видимых страниц, по каждой оси отдельно; скрытые страницы не в счёт. Все видимые страницы получают одно и то же место, показана текущая. Ширина — не меньше самого широкого ярлыка со стрелками прокрутки ярлыков (у драйвера Win32 — `Floor`).
- **Scroll.** Минимальный размер маленький — по полосам прокрутки, естественный равен естественному размеру ребёнка (в GTK для этого включены `propagate-natural-width/height`). Ребёнок получает видимую область, но не меньше своего минимума; если не помещается, появляются полосы прокрутки.

## 6. Как это ложится на GTK

| nui | GTK3 |
|---|---|
| `VBox`/`HBox` | `gtk_box_new(GTK_ORIENTATION_VERTICAL/HORIZONTAL, spacing)` |
| `Box.Spacing(px)` | `gtk_box_set_spacing` |
| `Box.Padding(px)`, `Grid.Padding`, `Window.SetPadding` | `gtk_container_set_border_width` |
| ребёнок Box | `gtk_box_pack_start(box, child, expand, TRUE /*fill*/, 0)`; `expand` = флаг `Expand(...)` |
| `Stretch()` | пустой `gtk_box_new(…, 0)`, упакованный с `expand = TRUE` |
| `NewGrid` | `gtk_grid_new` |
| `Grid.Add/AddSpan` | `gtk_grid_attach(grid, child, col, row, cols, rows)` |
| `Grid.Spacing` | `gtk_grid_set_column_spacing`, `gtk_grid_set_row_spacing` |
| `ExpandCol(c)` | `gtk_widget_set_hexpand(child, TRUE)` у детей, занимающих **только** колонку c (1×N) |
| `ExpandRow(r)` | то же с `vexpand` |
| `SetAlign(h, v)` | `gtk_widget_set_halign/valign`. Наш `Align` → `GtkAlign`: Fill→FILL(0), Start→START(1), Center→CENTER(3), End→END(2) |
| `SetMinSize(w, h)` | `gtk_widget_set_size_request` |

**Ловушка — распространение hexpand/vexpand в GTK.**
- В GTK3 флаг `hexpand` у ребёнка «всплывает» к родителям, если у родителя флаг не задан явно.
- `GtkBox` учитывает его **вдобавок** к `expand` при упаковке.

Без мер предосторожности Grid с растягиваемой колонкой начал бы растягиваться внутри HBox, а это нарушает правило из §3. Поэтому:

> Драйвер **каждому** создаваемому виджету и контейнеру явно вызывает `gtk_widget_set_hexpand(h, FALSE)` и `gtk_widget_set_vexpand(h, FALSE)`. После этого флаг считается «заданным», и всплытие прекращается. `TRUE` ставят только `ExpandCol` и `ExpandRow` у детей Grid, и дальше этого Grid флаг не уходит.

`Grid` хранит на стороне Go множество растягиваемых колонок и строк и список детей с их координатами. Так `ExpandCol`, вызванный **после** `Add`, проставит флаг уже вставленным детям, а вызванный **до** `Add` — будущим.

## 7. Движок для Win32 (`internal/layout`, фаза 5)

Это чистый Go без cgo, он тестируется на любой машине. Алгоритмы повторяют GTK 3.24 (`gtkbox.c`, `gtkgrid.c`, `gtkwidget.c`, `gtksizerequest.c`) вплоть до округлений, и это проверено golden-тестами (§8).

```go
type Size struct{ W, H int }
type Rect struct{ X, Y, W, H int }
type Insets struct{ L, T, R, B int }

type Node struct {
	Kind            uint8  // Leaf, VBox, HBox, Grid, Frame, Scroll, Stack
	Hidden          bool   // SetVisible(false)
	Expand          bool   // ребёнок Box забирает свободное место
	HAlign, VAlign  uint8  // AlignFill, AlignStart, AlignCenter, AlignEnd — как nui.Align
	Min, Nat, Floor Size   // Leaf: Min, Nat — от драйвера; контейнеры: Min, Nat считает Measure
	Inset           Insets // Frame, Scroll, Stack: оформление вокруг детей — от драйвера
	Padding         int    // Box.Padding, Grid.Padding
	Spacing, ColGap, RowGap int
	Col, Row, Cols, Rows    int    // ребёнок Grid
	ExpandCols, ExpandRows []bool
	Children []*Node
	Out      Rect // результат Arrange
}

func Measure(n *Node)            // снизу вверх: Min, Nat контейнеров; Floor — у всех
func Arrange(n *Node, cell Rect) // сверху вниз: Out всех видимых узлов
```

- **Floor** поднимает минимум и естественный размер узла, как size request в GTK: `Min = max(Min, Floor)`, `Nat = max(Nat, Min)`. Туда идёт `SetMinSize`. У `Frame` драйвер добавляет ширину заголовка, у `Scroll` — свой минимум (полосы прокрутки).
- **Out** — место узла без `Padding`, как allocation в GTK. Координаты отсчитываются от клиентской области окна, у потомков `Scroll` — при нулевой прокрутке.
- **Окно** — не узел. Драйвер раскладывает корень в `Rect{p, p, W−2p, H−2p}`, где `p` — `Window.SetPadding`, а минимальный размер клиентской области окна = `корень.Min + 2p`.
- **Выравнивание** (`adjust_for_align`): `Fill` занимает всю ячейку; `Start`, `Center`, `End` получают естественный размер, но не больше ячейки. Отступ контейнера вычитается после выравнивания.

**Box** (`gtk_box_size_allocate_no_center`), главная ось:

```text
vis := видимые дети
size := доступно − Spacing·(len(vis)−1) − Σmin(c)
sizes, size := distribute(max(0, size), vis)       // сначала до естественных размеров
each, extra := size / nExpand, size % nExpand      // остаток — растягиваемым (Expand, Stretch)
для c по порядку: s(c) = sizes(c) + (each + 1, пока extra > 0; extra−−, если c растягивается)
ячейка c: max(1, s(c)) по главной оси, max(1, поперёк); следующая начинается через s(c) + Spacing
```

Если места хватает на все естественные размеры, `distribute` выдаёт их, а остаток уходит растягиваемым. Если растягиваемых нет, свободное место остаётся в конце. Ячейка не бывает меньше 1 px: так GTK выделяет место и пустому `Stretch`. Позиция следующего ребёнка при этом сдвигается на настоящий размер, то есть на 0.

```text
distribute(space, sizes):  // gtk_distribute_natural_allocation; space ≥ 0 — место сверх минимумов
    size(c) = min(c) для всех
    порядок: разрыв gap(c) = max(nat(c) − min(c), 0) по убыванию, при равенстве — индекс по убыванию
    обход с конца порядка, i = n−1 … 0, пока space > 0:
        share := (space + i) / (i + 1)              // ⌈space / (i+1)⌉
        give  := min(share, nat(c) − min(c))        // без обрезки снизу
        size(c) += give; space −= give
    вернуть остаток space
```

«Без обрезки снизу» — тоже как в GTK. У линии Grid естественный размер может оказаться меньше минимального: ячейка на несколько линий поднимает минимумы своих линий больше, чем естественные размеры. Тогда при лишнем месте `distribute` сжимает такую линию до естественного размера. Пример есть в случае `grid-span`.

**Grid** (`gtkgrid.c`), сначала колонки, потом строки:
1. Линия непустая, если её занимает хоть одна видимая ячейка, в том числе на несколько линий. Пустые линии нулевые, промежутков вокруг них нет.
2. Минимум и естественный размер линии — максимум по видимым ячейкам на одну эту линию. Растягивается линия, если в ней есть видимая ячейка на одну линию, а линия помечена `ExpandCol` или `ExpandRow` (в GTK это `hexpand` ребёнка, §6).
3. Ячейки на несколько линий добирают недостающее (`gtk_grid_request_spanning`): из растягиваемых линий, а если таких нет — из всех; поровну с округлением вниз, остаток — последней. Отдельно для минимума и для естественного размера.
4. Размер Grid — сумма линий плюс промежутки между непустыми.
5. Раскладка линий — как Box (`distribute`, затем остаток поровну растягиваемым). Ячейка = сумма её линий + промежутки между ними, не меньше 1 px.

**Frame**: `Min = ребёнок.Min + Inset`, то же для `Nat`; затем `Floor` (ширина заголовка). Ребёнок получает `Out` за вычетом `Inset`.

**Scroll**: `Min` — только `Inset` и `Floor`; `Nat = ребёнок.Nat + Inset`. Ребёнок получает видимую область `Out − Inset`, но не меньше своего `Min` по каждой оси. Это семантика оверлейных полос прокрутки GTK: они не отнимают места у содержимого. На Win32 полосы занимают место. Когда они появляются, драйвер заново раскладывает ребёнка (`Arrange` поддерева) в уменьшенной видимой области.

Измерение листьев на Win32 и пересчёт по `WM_SIZE` и `WM_DPICHANGED` описаны в [driver-win32.md](driver-win32.md).

**Когда пересчитывать раскладку.** Узел помечается «грязным» в таких случаях:
- `WM_SIZE`;
- изменился текст, от которого зависит естественный размер (`SetText` у Label, Button, Check);
- `SetVisible`;
- `Add`;
- `SetMinSize`.

Пересчёт делается **один раз** на пачку изменений: первое изменение отправляет `PostMessage(WM_APP_RELAYOUT)`, повторные — нет.

## 8. Golden-тесты: эталон снимается с GTK

Цель — доказать, что `internal/layout` раскладывает так же, как GTK, и не зависеть при этом от шрифтов. Эталон снимает сам драйвер nui на GTK (ADR-18).

1. **Случаи.** Файлы `internal/layout/testdata/cases/*.txt` описывают дерево на простом текстовом языке (полное описание — в `internal/layout/golden`):

   ```text
   window 400x300 padding=12      # размер окна и Window.SetPadding
   vbox spacing=6
     fixed 100x20                 # лист ровно 100×20 (Separator + SetMinSize)
     label expand ellipsis "Подпись с многоточием"   # минимум меньше естественного
     hbox
       fixed 50x20
       stretch
       fixed 80x30 align=end,center
     grid colgap=6 rowgap=6 expandcol=1
       fixed @0,0 60x20
       fixed @1,0 100x20
       fixed @0,1 span=2x1 300x40
   ```

   - Листья — настоящие виджеты nui: `fixed WxH`, `label`, `button`, `check`, `entry`, `combo`, `slider`, `progress`, `textview`, `separator`, `stretch`.
   - Контейнеры: `vbox`, `hbox`, `grid`, `frame "заголовок"`, `scroll`.
   - Атрибуты: `expand`, `hidden`, `align=`, `min=` (`SetMinSize`), `@кол,стр`, `span=`, `spacing=`, `padding=`, `colgap=`, `rowgap=`, `expandcol=`, `expandrow=`.

2. **Сторона GTK** — интеграционный тест `TestLayoutGTK` (тег `gui`, `layout_gui_test.go`) идёт в обычном `make test`:
   - строит случай из виджетов nui и показывает окно заданного размера;
   - снимает с GTK минимальный и естественный размеры каждого узла и его прямоугольник в окне: `gtk_widget_translate_coordinates`, так что прокрутка тоже учитывается;
   - у `Frame` и `Scroll` снимает оформление (`Inset`) по месту ребёнка и собственный минимум (`Floor`). Для `Frame` это минимум с временно скрытым ребёнком, то есть ширина заголовка;
   - тут же сверяет движок: размеры листьев и оформление — вход, ожидаются прямоугольники всех узлов и размеры контейнеров. Поэтому тест проходит на любой машине, на любых шрифтах;
   - с `NUI_GOLDEN=write` записывает снимок `testdata/golden/<случай>.txt`. Снимки пишет `make golden` в контейнере `nui-bookworm`, чтобы они не зависели от машины разработчика.

3. **Сторона движка** — `TestGolden` (`internal/layout`, чистый Go) читает случаи и снимки и сверяет движок **точно**, без GTK — на любой ОС, в том числе на Windows. Расхождение в 1 px допускается только у случаев с `tolerance=1` у `window`, с комментарием, откуда оно берётся (сейчас таких нет).

Снимки хранятся в репозитории. Их перегенерируют при смене образа (версии GTK, темы, шрифтов), а изменения разбирают отдельно.

Случаи покрывают Box (растягивание, остаток по пикселю, скрытые дети, нехватка места), выравнивание, Grid (ячейки на несколько линий с растягиваемыми колонками и без, пустые линии), Frame и Scroll, вложенность с отступами и `SetMinSize` у контейнеров и форму из настоящих виджетов. Что тесты ловят ошибки, проверено мутациями движка: обрезка отрицательного разрыва в `distribute`, отсутствие минимума 1 px у ячейки, отступ внутри `Out`.

Тесты и код golden-тестов (`internal/layout/golden`) могут импортировать что угодно, включая `fmt` и `strings`: в бинарник приложения они не попадают. `make deps` проверяет только код библиотеки и запрещает ей импортировать `internal/layout/golden`.
