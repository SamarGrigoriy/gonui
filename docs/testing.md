# Тестирование

## 1. Уровни

| Уровень | Что проверяет | Тулчейн | Где запускается |
|---|---|---|---|
| Юнит-тесты `internal/core` | реестр, ud, диспетчер, очередь `Do` | gc (+ `-race`) | везде, без GTK и без cgo |
| Интеграционные (тег `gui`) | каждый виджет и правило из [api.md](api.md) на настоящем GTK и на драйвере Win32 | gc | Linux, `xvfb-run`; Windows — под Wine (`make win-test`, образ `nui-win`) |
| Selftest примеров | сборка, запуск, цикл событий, выход — обоими тулчейнами | gc, TinyGo | Linux, `xvfb-run` |
| Golden-тесты раскладки | движок Win32 (`internal/layout`) раскладывает так же, как nui на GTK ([layout.md](layout.md), §8) | gc | сторона GTK — Linux + Xvfb (`TestLayoutGTK`, в `make test`); снимки — `make golden` в контейнере; движок по снимкам — везде |
| Статические проверки | прототипы, импорты, размер | — | CI |
| Ручные чек-листы | то, что не автоматизируется: внешний вид, IME, доступность, диалоги, окружения | — | перед релизом |

## 2. Юнит-тесты `internal/core`

| Случай | Ожидание |
|---|---|
| `Register` → `Release` → `Register` | id переиспользуется; id 0 не выдаётся никогда |
| `Lookup` чужого или освобождённого id | `nil`, без паники |
| `UD`/`Decode` на границах (id = 1, 2²⁷−1; все Kind) | взаимно обратны |
| `Dispatch` с неизвестным id | возвращает 0, ничего не вызывает |
| `Dispatch(KDo)` | вызывает `Drain` |
| `Post` ×3 подряд | `true`, `false`, `false` (будим один раз) |
| `Drain`, внутри которого снова `Post` | новая функция не выполняется в этом же `Drain`; `Post` вернул `true` |
| `Post` после `Close` | `false`, функция не выполнится |
| Функция из очереди открыла «модальный диалог» (вложенный `Drain`) | остаток пачки выполняется во вложенном цикле, не дожидаясь возврата; порядок сохранён |
| 100 горутин × 1000 `Post` (`-race`) | нет гонок; порядок внутри каждой горутины сохранён |

Порог покрытия — 90 % (`go test -cover ./internal/core/...`). У движка раскладки `internal/layout` те же правила: юнит-тесты на посчитанных вручную примерах (Box, нехватка места, Grid с ячейками на несколько линий, Frame, Scroll) плюс golden-тесты; покрытие 100 %.

## 3. Интеграционные тесты (тег `gui`)

**Запуск:**

```sh
NO_AT_BRIDGE=1 G_DEBUG=fatal-criticals xvfb-run -a go test -tags gui ./...
```

`G_DEBUG=fatal-criticals` превращает любое `Gtk-CRITICAL` в падение: критическое предупреждение GTK — всегда наш баг.

**Устройство.** `Run` вызывается один раз на процесс. Пакет `testing` запускает **каждый тест в отдельной горутине** (`go tRunner(…)`), даже если `m.Run()` вызван из UI-потока. Поэтому вызывать `m.Run()` внутри обработчика нельзя: тесты пошли бы в GTK из чужого потока, а главный поток стоял бы в ожидании внутри колбэка. Схема обратная: цикл GTK крутится в главном потоке, `m.Run()` — в отдельной горутине, а тесты обращаются к виджетам через `ui`:

```go
//go:build gui

func TestMain(m *testing.M) {
	code := 0
	err := Run(func() {
		// Якорь: видимое окно на всё время тестов. Без него первое же закрытое тестом
		// окно завершило бы Run по ADR-15, и следующие тесты повисли бы.
		NewWindow("nui: интеграционные тесты", NewLabel("якорь")).Show()
		go func() { code = m.Run(); Do(Quit) }()
	})
	if err != nil { panic(err) }
	os.Exit(code)
}

// ui выполняет fn в UI-потоке и ждёт её завершения. Всё, что трогает nui, тест делает через ui.
func ui(fn func()) {
	done := make(chan struct{})
	Do(func() { fn(); close(done) })
	<-done
}

// waitUntil ждёт, пока cond (она выполняется в UI-потоке) не вернёт true, или таймаута.
// Нужна для асинхронных событий: таймеры, Watch, SimClose.
func waitUntil(cond func() bool, ms int) bool {
	deadline := time.Now().Add(time.Duration(ms) * time.Millisecond)
	for {
		ok := false
		ui(func() { ok = cond() })
		if ok || time.Now().After(deadline) {
			return ok
		}
		time.Sleep(5 * time.Millisecond)
	}
}
```

- `t.Parallel()` в GUI-тестах запрещён: у тестов один UI-поток и одно состояние GTK.
- Внутри `ui(…)` — только `t.Error`/`t.Errorf`, **не `t.Fatal`**: `FailNow` завершает горутину, в которой вызван, а `ui` выполняет функцию в главном потоке с циклом GTK.
- Кнопку по умолчанию GTK «нажимает» с задержкой ~250 мс (`activate` → `clicked` по таймеру): результат `SimEnter` ждать через `waitUntil`.
- Сценарии, которые должны завершить `Run` (автовыход, `Quit` в setup, нет дисплея), идут в дочернем процессе: тест запускает свой бинарник с переменной `NUI_HELPER=<сценарий>`, и `TestMain` выполняет сценарий вместо `m.Run()`.
- Если задан `NUI_SHOTS=<каталог>`, тесты раскладки снимают свои окна для фотоотчёта (`make shots`).
- Горутины и `time` в тестах разрешены: ADR-7 и ADR-11 касаются только не-тестового кода.
- Результат асинхронных действий (таймеры, `Watch`, `SimClose`) проверяется через `waitUntil`, а не однократным `ui`.

Сценарии, которые завершают процесс (например, уничтожение последнего видимого окна вызывает выход из `Run`), запускаются **в дочернем процессе** по стандартному приёму Go: тест повторно запускает свой же бинарник с `-test.run=TestHelperProcess` и переменной окружения, которая выбирает сценарий, затем проверяет код возврата и время выхода.

**Хелперы драйвера** (`internal/drv/sim_linux.go`, тег `gui`). Они имитируют **действия пользователя**: вызывают GTK напрямую, мимо `quiet`, поэтому `On*` срабатывают. Вызываются только внутри `ui(…)`.

| Хелпер | GTK |
|---|---|
| `SimClick(h)` | `gtk_button_clicked` |
| `SimType(h, s)` | `gtk_entry_set_text` |
| `SimEnter(h)` | `gtk_widget_activate` |
| `SimToggle(h)` | `gtk_toggle_button_set_active(!active)` |
| `SimSelect(h, i)` | `gtk_combo_box_set_active` |
| `SimSlide(h, v)` | `gtk_range_set_value` |
| `SimEdit(view, s)` | `gtk_text_buffer_set_text` |
| `SimClose(h)` | `gtk_window_close`: присылает `delete-event`, как крестик, но через idle-источник — результат ждать через `waitUntil` |
| `SimDialogResponse(resp int) bool` | C-хелпер: найти в `gtk_window_list_toplevels()` видимый модальный `GtkDialog` и вызвать `gtk_dialog_response` |
| `Allocation(h) (x, y, w, ht int)` | `gtk_widget_get_allocation` (`GtkAllocation` на стеке C-хелпера) |

C-хелперы для тестов лежат в `wrap_linux.c` под `#ifdef NUI_GUI_TEST`. Этот макрос включает `#cgo CFLAGS: -DNUI_GUI_TEST` в файле `sim_linux.go` (тег `gui`): директивы `#cgo` действуют на все C-файлы пакета, поэтому в обычную сборку хелперы не попадают.

**Каталог случаев:**

| Область | Случаи |
|---|---|
| Каждый виджет | `Set*`/геттер возвращают то же значение: кириллица, эмодзи, пустая строка, строка с `\x00` (обрезается); строка с невалидным UTF-8 (U+FFFD на месте битых байтов, без `Gtk-CRITICAL`) |
| Правило Set ≠ On (ADR-8) | `SetText`/`SetChecked`/`SetSelected`/`SetValue`, а также `Combo.Add`/`Clear` и `TextView.Append`/`Clear` → обработчик **не** вызван. `Sim*` → вызван: ровно один раз для Entry, Check, Combo, Slider; `SimEdit` на непустом TextView — дважды (удаление и вставка, так ведёт себя GTK) |
| Один обработчик | второй `OnClick` заменяет первый; `OnClick(nil)` снимает |
| Уничтожение | после закрытия окна: `Alive() == false`, сеттеры ничего не делают, геттеры возвращают нулевые значения, после `ui`-барьера нет критических предупреждений; `SetChild` уничтожает старого ребёнка |
| Вставка | повторная вставка → паника с текстом из контракта |
| Window | `OnClose` → `false` оставляет окно (`SimClose`, затем `waitUntil` вызова `OnClose` → `Alive()`); `Close()` не вызывает `OnClose`; в дочернем процессе: уничтожение видимого окна при живом скрытом завершает `Run` (ADR-15) |
| Entry | `OnEnter` задан → кнопка по умолчанию не срабатывает; не задан → срабатывает; Enter в поле ComboEntry нажимает кнопку по умолчанию |
| Combo | `Text()` у Combo и ComboEntry; `SetText` у Combo выбирает элемент; `Clear` → −1 |
| TextView | `Append("a\n")` … `Append("e\n")` + `SetMaxLines(3)` → `Text() == "c\nd\ne\n"` (завершающий `\n` не считается лишней строкой); то же без завершающего `\n`; `SetAutoScroll(true)` + выделение → после `Append` выделение на месте |
| Таймеры | `After` срабатывает один раз; `Every` + `Stop` изнутри — больше не срабатывает; `Stop` дважды безопасен |
| `Watch` | pipe: запись → `IORead`; закрытие пишущего конца → `IOHup`; `Stop` → больше не вызывается |
| `Do` | из горутины; из UI-потока (асинхронно: выполняется после возврата); порядок |
| Модальный диалог | пока открыт `Message`, `Every` продолжает тикать; ответы «Да», «Нет», Esc, OK (`drv.SimAnswer`, `SimEsc`, `SimOK`); родитель уничтожен, пока открыт `Ask` → `false` без падения |
| Файловые диалоги | `OpenFile` с фильтром, отмена, `SaveFile` с предложенным именем, `ChooseFolder` (`drv.SimChooserSet`, `SimChooserDone`); `OpenFiles`: два файла (`drv.SimChooserAdd` — как Ctrl+щелчок), один файл, отмена |
| Клавиши | `OnKey`: Ctrl+S и F5 окно забирает — до поля не доходят, `X` отдаёт — буква в поле, Ctrl+Enter забран — `OnEnter` поля не вызван; клавиша через настоящий цикл сообщений (`drv.SimKeyPosted`: на Windows — `WM_KEYDOWN` в очередь); `OnKey(nil)` — всё полю. Только Linux: русская раскладка — keyval «ы» на клавише S даёт `'S'`. `TextView.OnEnter`: Enter — обработчик без перевода строки, Shift+Enter — перевод строки, после `SetWrap` (на Windows поле пересоздаётся) Enter по-прежнему обработчику. Чат: многострочное сообщение |
| List | `SetRows` + текст ячеек так, как его получает виджет (`drv.ListCellText`: GtkTreeModel / `LVN_GETDISPINFOW`); `Select` молчит, выбор пользователем (`drv.SimListSelect`) — `OnSelect`; `drv.SimListActivate` — `OnActivate`; `Update`; миллион строк: `cell` вызвана меньше 10 000 раз; `SetRows(0, nil)`; уничтоженный список. Только Linux: размер 46×71, на который опирается Win32 |
| Image | PNG 120×80 → место 120×80; `SetFit(60, 0)` → 60×40; мусор и пустые данные → `ErrImage`, прежняя картинка остаётся; JPEG с EXIF Orientation = 6 → повёрнут; `SetFile` и ошибка чтения; `Clear`; методы уничтоженной картинки ничего не делают |
| Буфер обмена | туда и обратно: кириллица, эмодзи, переводы строк, пустой текст; дочерний процесс читает то, что положил родитель; `Chat.LastMessage` после `Add`, `Stream`, `Clear` |
| Оболочка | дочерний процесс с подставной программой по умолчанию (`mimeapps.list` во временном `XDG_CONFIG_HOME`): `OpenURI` и `ShowInFolder` без сессии D-Bus и с сессией без `FileManager1` |
| Раскладка (GTK) | `Expand` забирает свободное место; `Stretch` прижимает соседей; скрытый виджет не занимает места (замер через `drv.Allocation(h)` с тегом `gui`) |

### Windows

Те же тесты собираются под Windows (`GOOS=windows`, mingw-w64) и идут под Wine 8.0 в Xvfb: `NUI_IMAGE=nui-win tools/docker-run.sh make win-test`, обычная и отладочная сборка.
- Помощники `drv.Sim*` для Windows (`sim_windows.go`) шлют контролам и их родителям те же сообщения, что Windows при вводе: `BN_CLICKED`, `CBN_SELCHANGE`, `EN_CHANGE`, `WM_HSCROLL`, `WM_KEYDOWN VK_RETURN` через настоящий цикл. В открытом диалоге они нажимают кнопки: `TDM_CLICK_BUTTON` у `TaskDialog`, `WM_COMMAND` у `MessageBoxW` и файловых диалогов, `BFFM_SETSELECTIONW` у выбора папки.
- Только на Linux (`*_linux_test.go`): `Watch`, запуск без дисплея, `OpenURI`/`ShowInFolder` с подставной программой XDG, сверка раскладки с GTK (`TestLayoutGTK`).
- Различия платформ отмечены в тестах `runtime.GOOS`: `TextView.OnChange` при замене текста (Windows — один вызов).
- Несколько файлов в диалоге открытия `drv.SimChooserAdd` выбирает так, как это делает Windows: переходит в каталог и пишет имена в кавычках.
- Wine 8.0 не отдаёт тег EXIF Orientation через GDI+; поворот читает Go (`core.Orientation`), так что тест проверяет тот же путь, что работает на настоящей Windows.
- Wine 8.0 не умеет `os.RemoveAll` (`FileDispositionInfoEx`) — временные каталоги тестов под Windows убираются без проверки ошибок.

## 4. Selftest примеров

У каждого примера есть файл `selftest_on.go` (тег `selftest`) и пустой `selftest_off.go`. Так в обычной сборке нет ни `os`, ни разбора флагов. Внутри `setup` пример вызывает `selftest()`:

```go
//go:build selftest
package main

import "nui"

func selftest() { nui.After(300, nui.Quit) } // окно показано, цикл крутится, выход с кодом 0
```

```sh
timeout 20 xvfb-run -a ./bin/small/hello-selftest   # код 0 — прошло
```

Это единственный автоматический прогон, который проверяет **сборку TinyGo** на настоящем GTK. `go test` с TinyGo + cgo + GTK не используется.

Selftest логгера, кроме того, создаёт псевдотерминал (`posix_openpt` через свой C-хелпер) как поддельный последовательный порт. Он пишет в него строки и проверяет содержимое лог-файла ([acceptance.md](acceptance.md), §6).

## 7. Ручные чек-листы (перед релизом и в конце фаз 2–4)

**Окружения.**
- GNOME на Wayland и на X11 (`GDK_BACKEND=x11`).
- KDE Plasma (Breeze-GTK), XFCE.
- Масштаб: `GDK_SCALE=2` и дробный 125 % в GNOME.
- Тема: `GTK_THEME=Adwaita:dark`, высококонтрастная тема.

**Раскладка** (`examples/form`):
- окно растягивается и сжимается до минимума без наложений;
- `Expand` и `Stretch` ведут себя по [layout.md](layout.md);
- длинный текст с многоточием сокращается, без многоточия не даёт окну сжаться;
- колонки Grid ровные.

**Клавиатура:**
- Tab и Shift+Tab обходят виджеты в порядке добавления;
- Enter нажимает кнопку по умолчанию;
- Esc закрывает диалог;
- Alt+F4 вызывает `OnClose`.

**Ввод:**
- кириллица, эмодзи (Ctrl+.), IME (ibus-anthy или ibus-libpinyin) в Entry и TextView;
- копирование и вставка между приложениями.

**Доступность:** Orca читает подписи кнопок, состояние флажков, тексты меток.

**Диалоги:**
- Message, Alert, Ask работают с клавиатуры; в Ask Esc даёт `false`;
- фильтры OpenFile;
- SaveFile спрашивает о перезаписи;
- ChooseFolder;
- работа через портал (`GTK_USE_PORTAL=1`).

**Оболочка:**
- `OpenURI` для `https://` и `file://`;
- `ShowInFolder` в Nautilus, Dolphin и Thunar; запасной путь без `FileManager1`; при «холодном» запуске файлового менеджера открывается одно окно, а интерфейс не замирает.

**Клавиши:**
- `OnKey` в русской и английской раскладке на Windows 10 и 11 и в GNOME (X11 и Wayland): Ctrl+S, Ctrl+Shift+S, F5, Esc, стрелки, цифры цифрового блока;
- ввод в чат через ibus (китайский пиньинь): Enter заканчивает набор и не отправляет сообщение.

**Картинки:**
- снимки с телефона (EXIF-поворот), PNG с прозрачностью на цветной панели, GIF, BMP — на Windows 10 и 11;
- окно с картинкой переносится между мониторами 100 % и 150 %: картинка остаётся чёткой и того же размера в логических пикселях;
- большое фото (12 Мп) с `SetFit(480, 360)`: открывается без заметной задержки, память после загрузки — порядка размера файла, а не 48 МБ.

**Буфер обмена:**
- скопировать из nui и вставить в браузер и текстовый редактор, и обратно; многострочный текст на Windows вставляется в «Блокнот» строками;
- после выхода из программы текст остаётся в буфере (Linux — при запущенном менеджере буфера обмена).

**Нагрузка:**
- `TextView.Append` по 10 КБ каждые 50 мс в течение 10 минут при `SetMaxLines(5000)`: интерфейс отзывчив, память стабильна;
- `Do` ×100 000 из горутины: порядок сохранён, утечек нет.
- Горутина вызывает `Do` пачками раз в 20 мс в течение минуты: окно перерисовывается, текст метки обновляется, окно двигается и растягивается без задержек.

**Долгий прогон:** `examples/hello` с `Every(100)` работает 1 час; RSS не растёт.
